# signalridge Pi extensions

A monorepo of [Pi](https://pi.dev) extensions. Every directory under `packages/`
is independently publishable to npm and independently understandable; the
private root is never published and declares no Pi manifest.

Two of them are designed as a pair — start there.

---

## The pair: `pi-subagents` + `pi-workflows`

`pi-subagents` runs agents. `pi-workflows` decides which agents to run and in
what order. Neither reaches into the other: a workflow dispatches through a
typed event-bus protocol, and the subagent runtime stays the only thing that
knows what a model costs.

```
┌─ pi-workflows ─────────────────┐         ┌─ pi-subagents ─────────────────┐
│  what runs, and in what order  │         │  how an agent actually runs    │
│                                │ spawn-  │                                │
│  • agent() parallel() pipeline │ managed │  • model + thinking (tiers)    │
│  • phases, budgets, checkpoint │ ──────▶ │  • tools, skills, cwd          │
│  • journal + resume            │         │  • queue, concurrency, retry   │
│  • verify / judgePanel / gate  │         │  • transcripts, stop, isolation│
└────────────────────────────────┘         └────────────────────────────────┘
        └───── @signalridge/pi-subagents-protocol (shared wire contracts) ────┘
```

Install both — they are separate Pi packages, and the peer dependency documents
the requirement without auto-loading the other half:

```bash
pi install npm:@signalridge/pi-subagents     # >= 1.9.0, protocol v4
pi install npm:@signalridge/pi-workflows
```

A workflow is a plain JavaScript module. It fans work out; the runtime decides
how that fan-out is actually paid for:

```js
export const meta = { name: "audit", description: "Scan, then synthesize" };

const findings = await parallel([
  () => agent("Check for cross-package imports", { strength: "low" }),
  () => agent("Check for secrets", { strength: "low" }),
]);

return agent("Synthesize: " + JSON.stringify(findings), { strength: "high" });
```

### Who owns what

| Question | Answered by |
| --- | --- |
| What work happens, in what order, with what recovery | `pi-workflows` — its DAG, its journal, its resume |
| How much a step is *worth* | the script names a **strength** (`low` / `medium` / `high`) |
| Which model that strength becomes | `pi-subagents` — its Agent tier catalogue, its resolver |
| How wide a fan-out really goes | `pi-subagents` — a run reads `maxConcurrent` live and is clamped to it |
| Tools, skills, cwd, isolation, transcripts, stop | `pi-subagents`, for workflow children exactly as for any other agent |

### Why it is split this way

A workflow script is generated by the user's own model. If it could name a
model, a thinking level, or a tool policy, an LLM-authored file would be
choosing what the host pays and what the host exposes. So the script's entire
cost vocabulary is three words, and a `strengths` table — not the script — binds
each word to a tier the host defined:

```jsonc
// <agent dir>/workflows/settings.json, or the per-project settings file
{ "strengths": { "low": "cheap-search", "high": "deep" } }
```

`/workflows strength` edits that table and prints the tiers the host defines —
the one place both halves are visible. There is deliberately no second tier
configuration file, and no per-call `model` or `tier` option to reach past it.

The same reasoning shapes concurrency: a workflow does not configure it. A
workflow agent occupies one of `pi-subagents`' background slots like any other
agent, so a single setting governs the whole fleet.

Full detail lives in each package's README —
[`pi-workflows`](packages/pi-workflows/README.md) for the runtime globals,
resume semantics, and routing table;
[`pi-subagents`](packages/pi-subagents/README.md) for agent types, tiers,
FleetView, and scheduling.

## Install

Packages are installed individually; each package's own `pi.extensions`
manifest controls what Pi loads.

```bash
pi install npm:@signalridge/pi-subagents
pi install npm:@signalridge/pi-workflows
pi install npm:@signalridge/pi-lsp
pi install npm:@signalridge/pi-ask-user-question
```

> **Install any one package from a single source.** An npm copy alongside a
> local checkout of the same package loads both, and the duplicate registers its
> tools twice.

To run from this checkout, load the local directories and skip the installed
catalogue with `-ne`:

```bash
pi -ne -e ./packages/pi-subagents -e ./packages/pi-workflows
```

### Experimental

Marked `piExtension.lifecycle: experimental`, which keeps them out of a release
unless a changeset names them: `pi-recall`, `pi-codex-compact`, `pi-analytics`.

### Libraries

Not Pi extensions. They register no resources, hold no state, and are consumed
as ordinary npm dependencies — never listed in Pi's extension package map.

| Package | What it does |
| --- | --- |
| `pi-subagents-protocol` | Side-effect-free wire contracts for the managed subagent protocol |
| `pi-ui` | Shared bordered custom-UI adapter used by extension-owned dialogs |

## Boundaries

Packages communicate through Pi's public APIs and `pi.events`; no extension
imports another extension's source. Each package owns a defined area — the
footer, the input editor, the workflow journal, the subagent queue — and
consumes other packages' state without mutating it.

[`docs/package-boundaries.md`](docs/package-boundaries.md) is the ownership
matrix, including persistence boundaries and the one-declared-range rule for
shared rendering dependencies.

## Development

```bash
bun install --frozen-lockfile
bun run check     # format + lint + typecheck + test
```

Every package owns its own `lint`, `typecheck`, `test`, `format`, and `check`
scripts, runnable individually. Run `bun run check` before committing.

## Release

A change to a published package needs a changeset naming it:

```bash
bun run changeset
bun run changeset:status
```

The Actions workflow opens a Version Packages PR once changes reach `main`;
merging it publishes only the changed packages, via npm Trusted
Publishing/OIDC. See [`docs/releasing.md`](docs/releasing.md) for setup,
bootstrap, rate-limit, and recovery guidance.

The custom packer and integrity-safe publisher remain available for
bootstrap and recovery — not for normal Changesets releases:

```bash
bun run release:pack -- --package=pi-lsp
bun run release:publish:recovery -- --package=pi-lsp --dry-run
printf '%s' "$NPM_TOKEN" | bun run release:publish:token -- --token-stdin --package=pi-new-package --tag latest
```

Bootstrap and token mode require exactly one selected package. Experimental
packages are packed or published only when intentionally selected.
